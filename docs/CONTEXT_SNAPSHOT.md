# Context snapshot — конец этапа 5 (проект завершён по плану)

Дата: 2026-10-09 · Ветка: `claude/tender-galileo-vgpmyi` · Все 5 этапов реализованы. Дальше — развёртывание на сервере и доработки по обратной связи.

## Продукт (кратко)
Закрытый TG-бот: друзья создают заявки на оплату зарубежных сервисов, админ платит своей картой вручную, друзья возвращают рубли.
Типы заявок: PAYMENT_LINK, GIFT_CARD (код шифруется AES-256-GCM, удаляется через N дней после DONE), TOP_UP, OTHER.
Режимы оплаты клиента: PREPAY (по умолчанию), BALANCE (резерв с баланса), PAY_LATER (лимит долга).
Логины/пароли и реквизиты карт не запрашиваем и не храним; у карт админа — только метка и валюта.

## Принятые решения (подтверждены владельцем)
1. Карточки заявок — в личку админа (`ADMIN_CHAT_ID` опционален). Только русский.
2. BALANCE: резерв суммы расчёта → при DONE резерв превращается в списание, затем отдельной проводкой разница по факту.
3. Факт списания переводится в рубли по курсу ЦБ на момент DONE (админ может поправить вручную); валюта карты ≠ валюта заявки допустима.
4. Разница (переплата/доплата) автоматически идёт в ledger клиента + уведомление клиенту.
5. Отклонение после подтверждённой оплаты: деньги остаются на балансе клиента.
6. Инвайт: одноразовый, 72 ч. PAY_LATER лимит — в рублях. Напоминания 10:00 МСК. Бэкапы 14 дней. pnpm. Без лицензии.
7. Хостинг не выбран → **long polling** по умолчанию; webhook + Caddy — опциональный профиль compose.

## Решения, принятые мной на этапе 2 (проверь, если не согласен)
- **Формула разницы по факту:** `baseCost − actualRub`, где `baseCost = сумма × курс × (1 + запас)` (без наценки и фикса), `actualRub = факт в валюте карты × курс валюты карты`.
  Наценка и фикс — доход админа и в разницу не входят.
- **Все суммы в иностранной валюте хранятся в сотых долях** (exponent 2), включая JPY/KRW — для единообразия арифметики.
- **Ledger при PREPAY:** `PAYMENT_RECEIVED +total` при «Оплата получена» → `ORDER_CHARGE −total` и (если ≠0) `DIFF_ADJUST` при DONE. Баланс после DONE = разница.
- **Расчёт истекает и в AWAITING_PAYMENT** (не только в QUOTED). Если клиент перевёл деньги уже после истечения — придётся пересчитать; админ решает вручную. В PAYMENT_CHECK заявка не истекает.
- **Отмена клиентом из PAYMENT_CHECK разрешена** (оплата ещё не подтверждена), админу уходит предупреждение «проверь, не нужно ли вернуть перевод».
- **Диалоги — свой лёгкий движок** (`src/bot/wizard/engine.ts`), а не @grammyjs/conversations (убран из зависимостей): без replay-ловушек, состояние в памяти (черновик теряется при рестарте, TTL 30 мин).
- **`/methods` (CRUD способов перевода) частично вытащен из этапа 3** — иначе PREPAY-цикл нельзя пройти. Номера карт в инструкциях запрещены (Luhn-детектор), чтобы выполнить правило «никаких данных карт в БД»; указывать нужно телефон СБП/банк/получателя. Если нужно разрешить — убрать проверку в `admin-catalog.ts`.
- Режим оплаты (PREPAY/BALANCE/PAY_LATER) в диалоге создания заявки пока **не спрашивается** — всегда PREPAY. FSM уже поддерживает BALANCE/PAY_LATER (переходы с guard по `payMode`), UI — этап 3.
- Админ-защита (`requireAdmin`) навешана на конкретные команды, а не на весь композер (иначе перехватывала бы апдейты клиентов — поймано при e2e).

## Решения, принятые мной на этапе 3 (проверь)
- **Модель резерва:** `ORDER_RESERVE −сумма` сразу уменьшает баланс; при DONE — `ORDER_RELEASE +reserved`, `ORDER_CHARGE −total`, `DIFF_ADJUST`; при CANCELED/REJECTED/EXPIRED резерв возвращается автоматически (в одном месте — `OrderService.run`).
- **BALANCE при нехватке:** резервируется *доступный* баланс сразу (чтобы его не потратили параллельно), клиент доплачивает `payDueMinor = total − reserve` переводом; при «Оплата получена» пишется `PAYMENT_RECEIVED +due` и `ORDER_RESERVE −due`, итого под заявкой зарезервирован весь `total`.
- **Долг = отрицательный баланс.** PAY_LATER: при DONE вместо `ORDER_CHARGE` пишется `DEBT_OPEN −total`. Экспозиция лимита = `max(0, Σ открытых PAY_LATER-заявок + новая − баланс)`.
- **Пополнение при долге:** сначала `DEBT_REPAY`, остаток `TOPUP` (один клик админа).
- **Режим оплаты выбирается в диалоге заявки** (последний шаг, только если вариантов больше одного); баланс/лимит перепроверяются при подтверждении расчёта, поэтому устаревший выбор безопасен.
- Подтверждение пополнения идемпотентно (`UPDATE … WHERE status='PENDING'`). Отмена заявки из PAYMENT_CHECK в режиме BALANCE возвращает резерв, но уже переведённые клиентом деньги админ разбирает вручную (предупреждение админу уже есть).
- Напоминания о долге вынесены в этап 3 (в `scheduler.ts`), дедупликация через таблицу `Reminder`; напоминания о подписках и очистка кодов — этап 4.
- Миграция `20260103000000_order_pay_due` (`Order.payDueMinor`). Движок диалогов теперь поддерживает асинхронный `skip`.

## Доработка после этапа 5 — реквизиты присылает админ
По просьбе владельца: способ перевода (СБП / прямой перевод / наличные) выбирает **админ**, а не клиент, и сам присылает реквизиты (лимиты банков вроде «от 5 800 ₽» админ учитывает вручную).
- **Заявка:** клиент подтверждает расчёт → `AWAITING_PAYMENT` с `payMethodId = null`, клиенту «Админ пришлёт реквизиты», админу карточка с кнопками способов `r:<заявка>:<версия>:<способ>` → диалог «пришли текст» → текст уходит клиенту (с кнопками «Я оплатил»/«Отменить») и **нигде не сохраняется**; сообщение админа удаляется из чата. В БД: `payMethodId` + событие `OrderEvent` (статус не меняется, версия не растёт, поэтому остальные карточки не «протухают»; повторная отправка/смена способа разрешены).
- **«Я оплатил»** недоступно, пока нет реквизитов (`RequisitesNotSentError`; кнопки нет, подделка отбивается и в боте, и в API).
- **Пополнение:** клиент называет сумму → `TopUp` без способа → админ выбирает способ `p:<пополнение>:<способ>` и присылает реквизиты → клиенту «🧾 Отправить чек» `b:rc:<id>` (только владелец, только после реквизитов, только PENDING) → админу чек + карточка → подтверждение `t:<id>:ok`.
- **Каталог способов:** `PaymentMethod.instructions` стал необязательным «готовым текстом» (кнопка «Отправить сохранённый текст»; `-` = пусто). Заготовки: СБП, Прямой перевод, Наличные. Миграция `20260104000000_admin_sent_requisites` (`TopUp.methodId` nullable, замена старых заготовок).
- **API:** клиентский `confirm` без `methodId`; `POST /admin/orders/:id/requisites {version, methodId, text?}`; `payment.awaitingRequisites`, действие `send_requisites`, `/me` админа отдаёт способы; клиентам способы не отдаются. Mini App: клиент видит «Ждём реквизиты», у админа карточка «Реквизиты клиенту».
- **Решение, на которое стоит обратить внимание:** текст реквизитов от админа не проверяется на номера карт (админ вводит их сам и сам решает); защита «никаких данных карт в БД» обеспечивается тем, что текст не сохраняется и не логируется (проверено тестом по всем таблицам).
- **Тесты: 148** (+4 новых сценария + обновлены прежние под новый поток).

## Автоотправка реквизитов по сумме
По просьбе владельца («механизм автозаполнения на сервере»; выбран вариант «реквизиты по сумме, без участия админа»).
- **Модель:** `PaymentMethod.autoSend`, `minAmountMinor`, `maxAmountMinor` (миграция `20260105000000_method_autosend`); текст реквизитов — `instructions` (хранится в БД, не в git; номера карт запрещены Luhn-детектором). Команды: `/method_limits <id> <от> <до>|off`, `/method_auto <id> on|off`; `/methods` показывает границы и состояние автоотправки.
- **Выбор:** чистая функция `domain/auto-requisites.pickAutoMethod` — активный + автоотправка + непустой текст + сумма в границах (включительно); из подходящих первый по `sortOrder`, затем `id`.
- **Когда срабатывает** (`bot/auto-requisites.ts`): сразу после перехода заявки в `AWAITING_PAYMENT` (сумма = `payDueMinor`) — в боте и в API `confirm`; при создании пополнения (сумма пополнения). Клиент получает то же сообщение с реквизитами, что и от админа; в журнале `OrderEvent` — «Реквизиты отправлены автоматически: X» (actorId = null); админу — «🤖 отправлены автоматически» + обычная карточка (можно отправить другие реквизиты вручную).
- **Если ничего не подошло** — прежний ручной путь; админу в уведомлении указано, что автоспособы есть, но сумма не проходит по границам.
- **Гонки:** `setPayMethod` проверяет версию заявки и статус, при отмене/повторном клике автоотправка молча пропускается.
- **Решение:** API больше не отдаёт `payment.instructions` (готовый текст способа мог не совпасть с реквизитами, присланными вручную); реквизиты клиент видит только в чате.
- **Тесты: 159** (+11): выбор способа (границы включительно, порядок, неактивные/без текста), команды и их валидация, автоотправка по заявке (СБП < 5 800 ₽, прямой перевод ≥ 5 800 ₽), откат на ручной путь (> 640 000 ₽, способ выключен), пополнения, та же логика через API.

## Этап 5 — Telegram Mini App (сделано)
### Решения, принятые мной (проверь)
- **Структура:** `webapp/` — отдельный пакет pnpm-workspace (React 18, Vite 6, TS strict, `@telegram-apps/sdk` 3). Бэкенд раздаёт `webapp/dist` по `/app/` через `@fastify/static` (одно происхождение — CORS не нужен). Vite-зависимости заморожены на v6, чтобы собираться на Node 20 из Dockerfile.
- **Аутентификация:** `Authorization: tma <initData>` на каждый запрос; HMAC по алгоритму Telegram (`WebAppData`), `timingSafeEqual`, возраст `auth_date` ≤ `WEBAPP_INITDATA_TTL_SEC` (24 ч), допуск «из будущего» 5 мин. Роль и статус — из БД на каждый запрос (блокировка действует сразу). Rate limit 60 + 20/с на пользователя.
- **API — тонкая обёртка над теми же сервисами, что и бот** (`OrderService`, `ReportService`, ledger), список доступных действий (`actions`) вычисляется из автомата статусов, поэтому UI не может предложить недопустимое. Деньги наружу — строками в минимальных единицах. Код подарочной карты не отдаётся ни в каком виде. Уведомления (клиенту/админу) шлются теми же текстами/карточками, что и из бота; уведомление о выполнении вынесено в общий `bot/notify-done.ts`.
- **Ограничение Mini App:** чек/скриншот нельзя получить как Telegram `file_id` из Mini App — «Я оплатил» с обязательным чеком и пополнение баланса остаются в чате (приложение подсказывает и закрывается). Скриншот списания при «Выполнено» тоже только из чата.
- **CSP** на статике: `script-src 'self'`, `frame-ancestors` только клиенты Telegram. Хэшированные ассеты кешируются навсегда, `index.html` — `no-store`.
- Парсер SDK требует поле `signature` в initData (есть в реальном Telegram); приложение дополнительно умеет брать сырой initData из URL-хеша, если SDK его не распознал. `buildSignedInitData` для отладки добавляет фиктивный `signature` (сервер его не проверяет — достаточно HMAC).
- **Dockerfile переделан под workspace** (в рантайм копируется `node_modules`, `dist`, `webapp/dist`; миграции — `node_modules/.bin/prisma migrate deploy`). **Не собирался** (в окружении нет Docker).

### Сделано
- Backend: `src/http/api/{webapp-auth,errors,dto,order-input,client-routes,admin-routes,index}.ts`, `src/http/server.ts` (статика + заголовки), `WEBAPP_URL` (кнопка меню чата, `/app`, кнопка в меню клиента), конфиг `WEBAPP_DIST`, `WEBAPP_INITDATA_TTL_SEC`.
- Frontend: экраны клиента (заявки, карточка с действиями, новая заявка с подсветкой ошибок по полям, баланс) и админа (очередь, карточка с формой «Выполнено», статистика); тема Telegram через CSS-переменные SDK, кнопка «Назад» Telegram, тосты, блокировка кнопок на время запроса, обработка `stale`.
- Инструменты: `pnpm webapp:dev|build|link|smoke`; `scripts/webapp-smoke.ts` — прогон в настоящем Chromium со скриншотами.
- **Тесты: 144** (+13): `validateInitData` (подделка, чужой токен, лишнее неподписанное поле, возраст, будущая дата, битый user), API на реальной БД (401/403 для всех видов плохих учёток, блокировка, чужие заявки = 404, клиент не видит админку, валидация как в боте, полный цикл через API с защитой от устаревшей версии и параллельных кликов, подарочная карта: код не утекает в ответы, новая ссылка/продление/пересчёт, статика и заголовки) + дымовой тест в браузере (13 экранов).
