# Закрытый Telegram-бот для учёта оплаты зарубежных сервисов

Бот автоматизирует учёт: заявки друзей, расчёт суммы в рублях, приём оплаты, статусы, балансы, история, напоминания.
Саму оплату картой админ делает вручную. **Бот не хранит и не обрабатывает реквизиты банковских карт** — только метки вида «Visa ··4417».

> Статус: **все 5 этапов** (+ Telegram Mini App). См. `docs/CONTEXT_SNAPSHOT.md`. См. `docs/CONTEXT_SNAPSHOT.md`.

## Стек
Node.js 20.19+ (в Docker — 22), TypeScript (strict), pnpm, grammY, PostgreSQL + Prisma 7 (драйверный адаптер `pg`, адрес БД для CLI — в `prisma.config.ts`), Fastify, Zod 4, pino 10, Vitest, ESLint + Prettier, Docker.

## Быстрый старт (локально, long polling)
```bash
pnpm install
cp .env.example .env            # заполни BOT_TOKEN, ADMIN_TELEGRAM_ID, ENCRYPTION_KEY, POSTGRES_PASSWORD
openssl rand -base64 32         # → ENCRYPTION_KEY
docker compose up -d db         # только база
pnpm prisma migrate deploy
pnpm dev
```
Без Docker подойдёт любой PostgreSQL 14+: поправь `DATABASE_URL`.

## Запуск на сервере (VPS)
```bash
git clone <repo> && cd <repo>
cp .env.example .env            # заполнить; BOT_MODE=polling не требует домена и HTTPS
cp backup.env.example backup.env  # ключ шифрования бэкапов и внешнее хранилище (см. ниже) — обязательно
docker compose up -d --build    # db + app + backup
docker compose logs -f app
```
Миграции применяются автоматически при старте контейнера `app`.

### Бэкапы (зашифрованные, с копией наружу)
Контейнер `backup` каждую ночь делает `pg_dump` → gzip (с проверкой целостности) → **шифрование age** → `./backups/daily/`, хранит 14 дней и (если настроено) копирует файл в S3-совместимое хранилище через rclone.
Шифрование — **публичным ключом**: на сервере хранится только он, поэтому украденный сервер или хранилище не раскрывают содержимое бэкапов.
1. На своём компьютере: `age-keygen -o age-key.txt` (пакет `age`). Публичный ключ (`age1…`) впишите в `backup.env` → `BACKUP_AGE_RECIPIENT`. Файл `age-key.txt` спрячьте (менеджер паролей и офлайн-копия) — **без него бэкап не расшифровать**.
2. Настройте копию наружу (`BACKUP_RCLONE_REMOTE`, `RCLONE_CONFIG_OFFSITE_*` в `backup.env`) — бэкап на том же сервере не спасёт от потери сервера. Эти секреты видит только контейнер `backup`, не приложение.
3. Первый бэкап делается через 30 секунд после запуска контейнера — проверьте: `docker compose logs backup` и `ls backups/daily`.
4. **Проверка восстановления** (сделайте хотя бы раз, потом периодически): `scripts/verify-encrypted-backup.sh backups/daily/<файл>.age age-key.txt postgresql://bot:<пароль>@localhost:5432` — расшифрует, развернёт во временной БД и проверит ключевые таблицы.
5. **Восстановление:** в пустую БД — `scripts/restore-backup.sh <файл>.age age-key.txt postgresql://bot:<пароль>@localhost:5432/bot`.

Бот следит за бэкапами: если последний успешный бэкап старше `BACKUP_MAX_AGE_HOURS` (по умолчанию 36 ч), он завершился ошибкой (в т.ч. не удалась выгрузка наружу) или бэкапов нет — вам приходит сообщение.
⚠️ Коды подарочных карт в БД зашифрованы `ENCRYPTION_KEY` — его тоже **храните отдельно от бэкапов** (без него коды из бэкапа не прочитать).

### Оповещения и самодиагностика
Бот сам пишет админу (не чаще раза в час на один тип проблемы, без персональных данных): об ошибках в обработчиках, в Mini App API и планировщике, о критическом сбое с перезапуском процесса, о перезапуске бота, об устаревших/неудачных бэкапах, о недоступности ЦБ и резком скачке курса. Контейнер `app` имеет `HEALTHCHECK` (`/health` проверяет и БД) и `restart: unless-stopped`.

### Ротация `ENCRYPTION_KEY`
Шифртекст хранит номер ключа, поэтому менять ключ можно без остановки: (1) `openssl rand -base64 32` → новый ключ; (2) в `.env`: старый перенесите в `ENCRYPTION_KEYS_OLD="1:<старый base64>"`, новый — в `ENCRYPTION_KEY`, `ENCRYPTION_KEY_ID=2`; (3) перезапустите бот; (4) `pnpm keys:rotate --dry-run`, затем `pnpm keys:rotate` перешифрует все коды новым ключом. Старый ключ храните, пока живы бэкапы со старым шифртекстом.

**Webhook (по желанию):** нужен домен с A-записью на сервер. В `.env`: `BOT_MODE=webhook`,
`WEBHOOK_URL=https://<домен>/webhook`, `WEBHOOK_SECRET=<16+ символов>`, `DOMAIN=<домен>`; запуск:
`docker compose --profile webhook up -d --build` (Caddy сам получит сертификат).

## Как создать первого клиента
1. Напиши боту `/start` со своего аккаунта (ID из `ADMIN_TELEGRAM_ID`) — получишь меню админа.
2. `/invite Вася` — бот пришлёт одноразовую ссылку `https://t.me/<bot>?start=<код>` (действует 72 ч).
3. Друг открывает ссылку и жмёт Start — регистрируется, тебе приходит уведомление.
4. Все остальные получают вежливый отказ.

## Как работает заявка
1. Клиент: «➕ Новая заявка» → тип (ссылка / подарочная карта / пополнение / другое) → ссылка → сервис → сумма и валюта → разовая или подписка → комментарий → «Отправить».
2. Админ получает карточку: тип, сервис, сумма, домен (✅ доверенный / ⚠️ НЕИЗВЕСТНЫЙ ДОМЕН), возраст заявки. Кнопка «🧮 Рассчитать».
3. Клиент видит итог в рублях → «Подтвердить» (способ перевода он **не выбирает**) → ждёт реквизиты. Тебе приходит карточка с кнопками способов («📤 СБП», «📤 Прямой перевод», «📤 Наличные»): нажимаешь нужный (удобно под сумму — например, если у способа есть минимальный лимит), присылаешь реквизиты текстом, бот пересылает их клиенту и убирает твоё сообщение из чата. Клиент переводит → «Я оплатил» (+чек, если способ требует).
   **Реквизиты, которые ты присылаешь вручную, нигде не сохраняются** — ни в БД, ни в журнале (там только «реквизиты отправлены: СБП»). Можно отправить повторно или выбрать другой способ, пока заявка ждёт оплату.
   **Автоотправка (без твоего участия):** если у способа задан текст реквизитов, границы суммы и включена автоотправка, сервер сам выбирает способ по сумме к переводу и сразу присылает клиенту реквизиты; тебе приходит уведомление «🤖 отправлены автоматически», дальше всё как обычно (клиент платит → ты подтверждаешь поступление). Если сумма не подходит ни под один способ — карточка приходит тебе для ручной отправки, с пометкой почему. То же для пополнения баланса.
4. Админ: «✅ Оплата получена» (или «🚫 Оплата не найдена») → в статусе «В работе» появляется кнопка «🔗 Открыть ссылку».
5. Админ платит картой вручную → «✅ Выполнено» → карта → фактическое списание → курс → (скриншот) → подтверждение.
   Бот считает разницу и записывает её в баланс клиента. Для подарочных карт код вводится при «Выполнено» и уходит клиенту; в БД хранится зашифрованным.

## Telegram Mini App
React + Vite + TypeScript + `@telegram-apps/sdk` (папка `webapp/`), раздаётся тем же Fastify-сервером по `/app/`.
- **Клиент:** «Заявки» (список, карточка, подтверждение расчёта, ожидание реквизитов, оплата, отмена, пересчёт, новая ссылка, продление подписки), «Новая» (форма заявки с проверкой на сервере), «Баланс» (баланс/долг и история).
- **Админ:** «Очередь» (открытые заявки, метка домена ✅/⚠️, возраст), карточка с действиями (рассчитать, **отправить реквизиты клиенту** — способ + текст, оплата получена / не найдена, ссылка не работает, отклонить, выполнено — карта, факт, курс, код подарочной карты), «Статистика».
- **Что остаётся в чате:** отправка чеков и скриншотов (Telegram отдаёт боту только `file_id` из чата, не из Mini App) и пополнение баланса. Приложение подсказывает и закрывается кнопкой «Вернуться в чат».

**Безопасность API (`/api`):** каждый запрос подписан — `Authorization: tma <initData>`; сервер проверяет HMAC по токену бота (по алгоритму Telegram), возраст `auth_date` (`WEBAPP_INITDATA_TTL_SEC`), затем берёт роль из БД (админ — `ADMIN_TELEGRAM_ID`). Заблокированные и неизвестные получают 403. Чужие заявки выглядят как несуществующие (404), админские маршруты проверяют роль в каждом запросе, действия защищены версией заявки (409 при устаревшей), коды подарочных карт через API не отдаются никогда, ссылки и числа валидируются теми же правилами, что в боте. Раздача статики идёт с `Content-Security-Policy` (встраивать можно только клиентам Telegram) и без кеширования `index.html`.

### Подключение
1. Нужен публичный **HTTPS**-адрес (Telegram не открывает http): домен с A-записью на сервер.
2. В `.env`: `WEBAPP_URL=https://<домен>/app/` и `DOMAIN=<домен>`. Режим бота может оставаться `polling` — домен нужен только для Mini App.
3. `docker compose --profile https up -d --build` — Caddy сам выпустит сертификат. Образ собирает и бота, и `webapp/dist`.
4. При старте бот ставит кнопку меню «Приложение»; у клиентов также кнопка «📱 Приложение» в меню и команда `/app`.

### Локальная разработка и проверка
```bash
pnpm install
pnpm webapp:dev                 # Vite на :5173, /api проксируется на :3000
pnpm webapp:build               # сборка в webapp/dist (раздаётся бэкендом)
pnpm webapp:link <telegramId>   # ссылка с подписанным initData для отладки (по BOT_TOKEN из .env)
TEST_DATABASE_URL=postgresql://... SHOTS_DIR=/tmp/shots pnpm webapp:smoke   # прогон в настоящем Chromium + скриншоты
```
Для проверки в самом Telegram нужен HTTPS-туннель (например, cloudflared / ngrok) на порт 3000 и `WEBAPP_URL` с адресом туннеля. `webapp:smoke` требует `playwright-core` и Chromium (`CHROME_PATH`).

## Подписки и напоминания
- При «Выполнено» для подписки ставится дата следующего списания (месяц / год / свой период).
- За `subscriptionRemindDays` дней (по умолчанию 3) после `reminderHour` (10:00 по `TIMEZONE`) клиент и админ получают напоминание. У клиента кнопки **«🔁 Продлить»** (создаётся новая заявка с теми же данными; клиент присылает свежую ссылку и заново выбирает режим оплаты) и **«Не продлевать»** (напоминания прекращаются).
- Одно напоминание на каждое списание; для подписки с уже оформленным продлением и для заблокированных клиентов напоминаний нет. `/subs` — список подписок по ближайшему списанию.
- Коды подарочных карт стираются из БД через `giftCodeRetentionDays` (по умолчанию 7) дней после «Выполнено» — проверка каждые 5 минут.
- Напоминания о долге — раз в `debtReminderDays` дней.

## Статистика и экспорт
`/stats [период]` — созданные и выполненные заявки, **оборот** (выставлено клиентам), **фактические расходы**, **валовая прибыль** (оборот − расходы: наценка + комиссия + курсовая разница), пополнения и погашения, разбивка по клиентам / сервисам / картам.
`/export [период]` — два CSV-файла: заявки и операции баланса. В заявках только домен ссылки (не вся ссылка), коды подарочных карт не экспортируются, ячейки со свободным текстом защищены от формул Excel (`=`, `+`, `-`, `@`). Файлы в UTF-8 с BOM, разделитель запятая, суммы в рублях через точку (в Excel: «Данные → Из текста/CSV»; в Google Sheets открывается сразу).
Период: `month` (по умолчанию), `prev`, `week`, `today`, `all`, `2026-09`, `2026-09-15`, `2026-09-01 2026-09-30` — в часовом поясе `TIMEZONE`. Для заявок период считается по дате создания, в статистике — по дате выполнения.

## Режимы оплаты клиента
В диалоге заявки последним шагом клиент выбирает режим (шаг пропускается, если доступен только перевод):
| Режим | Как работает |
|---|---|
| 💳 **Перевод (PREPAY)** | Клиент переводит итог до того, как ты платишь. По умолчанию. |
| 💰 **С баланса (BALANCE)** | Доступен при положительном балансе. При подтверждении расчёта сумма **резервируется**. Если баланса хватает — заявка сразу «В работе». Если нет — резервируется весь баланс, а разницу клиент **доплачивает переводом**. Отмена, истечение или отклонение возвращают резерв на баланс. |
| ⏳ **Оплата позже (PAY_LATER)** | Только если ты включил: `/paylater <id> on <лимит ₽>`. Лимит проверяется при подтверждении (долг + открытые заявки «в долг» + новая ≤ лимита), заявка сразу «В работе». Долг (`DEBT_OPEN`) возникает при «Выполнено». Напоминания раз в `debtReminderDays` дней после `reminderHour`. |

Баланс клиента — **только сумма проводок** `LedgerEntry`; отрицательный баланс = долг. Проверка баланса и лимита идёт под блокировкой строки клиента, поэтому параллельные заявки не потратят одни и те же деньги.
Пополнение (`➕ Пополнить баланс`): клиент называет сумму → ты выбираешь способ и присылаешь реквизиты (так же, как по заявке) → клиент присылает чек («🧾 Отправить чек») → ты подтверждаешь кнопкой. Если есть долг, сначала гасится он (`DEBT_REPAY`), остаток идёт на баланс (`TOPUP`).

**Расчёт:** `итог = сумма × курс × (1 + запас) × (1 + наценка) + фикс`, округление вверх до целых рублей. Курс — ЦБ РФ (кеш 1 час) или ручной (`/rate`). Параметры и курс фиксируются в заявке на момент расчёта.

**Проверка курса перед расчётом.** Нажимая «Рассчитать», админ получает предупреждение (и должен подтвердить «Рассчитать всё равно»), если курс сомнителен: ЦБ не отвечает дольше `rateStaleHours` (6 ч), курс резко изменился между обновлениями (порог `rateJumpBp`, 5%), ручной курс (`/rate`) старше 3 суток или расходится с ЦБ больше порога. После подтверждения повторные вопросы по этой валюте не задаются час. О скачке курса по используемым валютам бот оповещает сам, не дожидаясь расчёта. Последние курсы ЦБ сохраняются в БД — после перезапуска при недоступном ЦБ бот продолжит работать по ним (с предупреждением «курс устарел»). В Mini App то же самое: «Проверьте курс перед расчётом» с кнопкой подтверждения.

**Разница по факту:** `оценка себестоимости (сумма × курс × (1 + запас)) − фактическое списание в ₽`.
Положительная — переплата клиента (зачисляется на баланс), отрицательная — доплата (списывается). Наценка и фикс. комиссия в разницу не входят — это доход админа.

## Команды
**Клиент:** кнопки меню «➕ Новая заявка», «📋 Мои заявки», «💰 Мой баланс» (баланс/долг и история), «➕ Пополнить баланс»; `/cancel` — отменить диалог.

**Админ:**
| Команда | Что делает |
|---|---|
| `/invite [заметка]`, `/invites` | создать инвайт / список активных |
| `/clients`, `/block <id>`, `/unblock <id>` | клиенты (с балансами), блокировка |
| `/client <id>` | карточка клиента: статус, баланс/долг, последние операции |
| `/debts` | кто мне должен и у кого переплата/остаток |
| `/adjust <id> <±сумма ₽> [комментарий]` | ручная корректировка баланса (проводка `MANUAL_ADJUST`, клиент получает уведомление) |
| `/paylater <id> on [лимит ₽] \| off` | включить/выключить «оплату позже» и задать лимит долга |
| `/settings [ключ значение]` | запас на конвертацию, наценка, фикс. комиссия, TTL расчёта и др. |
| `/domains`, `/domain_add`, `/domain_del` | доверенные платёжные домены |
| `/orders` | открытые заявки |
| `/stats [период]`, `/export [период]`, `/subs` | статистика, CSV-выгрузка, список подписок |
| `/rate`, `/rate USD 95,5`, `/rate USD clear` | курсы: показать / задать вручную / вернуть ЦБ |
| `/cards`, `/card_add Visa ··4417 USD`, `/card_toggle <id>` | твои карты: только метка и валюта |
| `/methods`, `/method_add Название \| Текст реквизитов или - \| да`, `/method_edit <id> \| Текст или -`, `/method_receipt <id> да\|нет`, `/method_toggle <id>` | способы перевода (СБП, прямой перевод, наличные…). Текст реквизитов необязателен: если он есть, его можно отправить одной кнопкой, а при включённой автоотправке — автоматически. Нужен ли чек — настраивается на способ |
| `/method_limits <id> <от ₽> <до ₽>` (`-` = без границы) / `off` | границы суммы перевода для способа, например `/method_limits 2 5800 640000` |
| `/method_auto <id> on\|off` | автоотправка реквизитов этого способа по сумме (нужен текст реквизитов) |

Реквизиты ты вводишь вручную по каждой заявке, поэтому ограничений на формат нет, но бот их не сохраняет и не пишет в логи. Текст реквизитов способа хранится в БД бота (не в git) — номера банковских карт в нём запрещены (бот их не принимает): указывай телефон СБП, банк и получателя.

## Первичная настройка после запуска
```
/card_add Visa ··4417 USD
# способы «СБП», «Прямой перевод» и «Наличные» уже заведены; реквизиты можно присылать вручную по каждой заявке
# или настроить автоотправку по сумме (например, СБП до 5 799,99 ₽ и прямой перевод от 5 800 ₽):
/method_edit 1 | СБП: +7 900 000-00-00, Т-Банк, получатель Иван И.
/method_limits 1 - 5799.99
/method_auto 1 on
/method_edit 2 | Прямой перевод: +995 555 00 00 00, Example Bank, IVAN IVANOV
/method_limits 2 5800 640000
/method_auto 2 on
/method_add Наличные в офисе | Тверская, 1, с 10 до 19 | нет    # пример способа с готовым текстом
/rate USD 95        # необязательно: иначе берётся курс ЦБ
/settings markupBp 5
```

## Разработка
```bash
pnpm check        # lint + prettier + типы (бот и Mini App) + тесты — то же, что гоняет CI
pnpm lint:fix && pnpm format
```
CI (GitHub Actions, `.github/workflows/ci.yml`): линтер, форматирование, типы, сборка бота и Mini App, миграции и все тесты на PostgreSQL 16, `pnpm audit` (падает на high+), сканирование секретов gitleaks по всей истории. Dependabot обновляет зависимости еженедельно.
Локально бот читает `.env` сам (`process.loadEnvFile`); для CLI Prisma адрес БД берётся из `DATABASE_URL` через `prisma.config.ts`.

```bash
pnpm test         # юнит-тесты
TEST_DATABASE_URL=postgresql://... pnpm test   # + интеграционные и e2e с подставным Telegram (БД будет очищена!)
pnpm typecheck
pnpm build
```

## Архитектура
`src/bot` (хендлеры, middleware, клавиатуры) · `src/http` (Fastify: webhook, `/api` Mini App, статика) · `webapp/` (Mini App) · `src/domain` (чистая логика: деньги, настройки, домены) ·
`src/services` (БД-сервисы, шифрование, rate limit) · `src/db` · `src/http` · `src/texts` (все тексты).

Безопасность: роль проверяется middleware на каждое обновление (+ `requireAdmin` в админских композерах);
инвайт гасится атомарно в транзакции; `LedgerEntry` и `OrderEvent` защищены от UPDATE/DELETE триггером БД;
деньги — `BigInt` в минимальных единицах; логи без текстов сообщений, ссылок и кодов; работа только в личных чатах.
